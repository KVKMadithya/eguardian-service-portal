    Production SQL — KPI Queries

    PostgreSQL queries against the relational requests table that reproduce each dashboard KPI. The demo pins "today" to 2026-10-30; production uses CURRENT_DATE.

    1. Open Requests 
    SELECT COUNT(*) AS open_requests
FROM requests
WHERE status IN ('Submitted', 'Under Review', 'Approved');
    2. Avg Days to Approval 
    SELECT ROUND(
         COALESCE(AVG(approved_at - created_at), 0)::numeric, 1
       ) AS avg_days_to_approval
FROM requests
WHERE status IN ('Approved', 'Completed')
  AND approved_at IS NOT NULL;
    3. Approval Rate (%) 
    SELECT ROUND(
         COALESCE(
           100.0 * COUNT(*) FILTER (WHERE status IN ('Approved', 'Completed'))
           / NULLIF(COUNT(*) FILTER (WHERE status IN ('Approved', 'Completed', 'Rejected')), 0),
           0
         ), 1
       ) AS approval_rate_pct
FROM requests;
    4. Overdue Requests (>7 Days SLA) 
    SELECT COUNT(*) AS overdue_requests
FROM requests
WHERE status IN ('Submitted', 'Under Review', 'Approved')
  AND created_at < CURRENT_DATE - INTERVAL '7 days';

    Request Workflow

    Submit new requests and move them through the enforced approval state machine.

    Enforced State Machine (VALID_TRANSITIONS)

    Submitted ➔ Under Review ➔ Approved ➔ Completed terminal OR Rejected terminal

    Any transition not listed is blocked client-side. Only the Manager role can move requests; approving stamps approvedAt and every move appends to statusHistory.

    Sample Dataset

    Synthetic, fully anonymized service requests.

    Data Generation Methodology

    • 36 records (REQ-1001–REQ-1036) created between 1 Sep and 28 Oct 2026, roughly 3–4 per week, so the trend chart has a realistic shape.
    • Every department, request type, priority and status is represented, so all filters and chart segments have data.
    • Each statusHistory was generated by walking the same state machine the app enforces: Submitted → Under Review (next day) → Approved/Rejected → Completed (two days after approval).
    • 12 open requests are deliberately older than 7 days so the Overdue KPI is populated.
    • Zero real PII: requesters are sequential placeholders EMP-101–EMP-136; approvers are recorded by role ("Manager"), never by name. Titles and descriptions are generic business scenarios.
    • Data lives in the browser's localStorage (eguardian_requests_v1); Reset Demo Data restores the original 36 records.

    Requirements

    Problem, users, user stories, briefing outcomes, assumptions and data model.

    Problem Statement

    eGuardian's internal service requests — access grants, equipment, maintenance, licenses and cloud resources — are currently raised by email and tracked in departmental spreadsheets. Requests get lost between inboxes, there is no consistent approval path or audit trail, requesters cannot see where their request stands, and leadership has no reliable view of backlog, approval speed or SLA breaches. This portal replaces that fragmented process with one centralized request workflow that enforces a fixed approval lifecycle, records who changed what and when, and feeds an executive dashboard of live KPIs.

    Target Users

    Staff

    Employees in any department who raise requests. They need a quick validated form and visibility of each request's status and history.

    Managers

    Approvers who triage the queue, review, approve or reject with a note, and confirm completion — within a controlled, auditable lifecycle.

    Leadership

    Executives who need read-only, filterable KPIs on backlog, approval speed, approval rate and SLA breaches across departments.

    User Stories & Acceptance Criteria

    US-01 Submit a request

    As a staff member, I want to submit a service request through one form so that it is tracked centrally instead of by email.

    Given
    I am in Staff View on the Workflow tab
    When
    I submit a form with a valid title, Employee ID, department, type, priority and description
    Then
    a new REQ- ID is created in Submitted status, appears at the top of the queue, and the dashboard KPIs update immediately

    US-02 Get clear validation feedback

    As a staff member, I want to see what is wrong with my input so that I can correct it before submitting.

    Given
    I enter an Employee ID that does not match EMP-xxx or a description under 15 characters
    When
    I press Submit Request
    Then
    an inline error appears under each invalid field and no record is created

    US-03 Triage incoming requests

    As a manager, I want to move new requests into review so that requesters know they are being handled.

    Given
    I am in Manager View and a request is Submitted
    When
    I click Move to Review
    Then
    its status becomes Under Review and a history entry records the new status, timestamp and actor "Manager"

    US-04 Approve or reject with a note

    As a manager, I want to approve or reject with a reason so that decisions are documented.

    Given
    a request is Under Review and I have opened its History modal
    When
    I enter a manager note and click Approve (or Reject)
    Then
    the status updates, approvedAt is set to today on approval, and my note is saved in the status history

    US-05 Prevent invalid status changes

    As a process owner, I want the lifecycle enforced so that requests cannot skip review or be reopened.

    Given
    a request is Submitted, Rejected or Completed
    When
    anyone attempts a transition not listed in VALID_TRANSITIONS (e.g. Submitted → Approved)
    Then
    the change is blocked, an error toast is shown, and the record is unchanged

    US-06 Filter executive KPIs

    As a leader, I want to slice KPIs by department, status, priority and date so that I can spot bottlenecks.

    Given
    I am in Leadership View on the Dashboard
    When
    I set Department = Security and a date range
    Then
    all 4 KPIs and 3 charts recalculate on matching records only, and an empty result shows 0.0 / 0.0% rather than NaN

    US-07 Audit trail and data export

    As an auditor or leader, I want to see each request's full history and export the dataset so that decisions can be reviewed offline.

    Given
    any role is active
    When
    I click History on a request, or Download CSV / Download JSON on the Sample Dataset tab
    Then
    the history is shown in chronological order with actor and note, and the file downloads with quotes escaped and spreadsheet formulas neutralised

    US-08 Role-specific views

    As any user, I want the portal to show what matters for my role so that I am not wading through actions I cannot take.

    Given
    I switch the Role selector to Staff, Manager or Leadership
    When
    the view changes
    Then
    Staff land on Workflow showing My requests with their Employee ID locked (they cannot submit as anyone else, and any direct status-change attempt returns Access Denied); Managers land on Workflow showing Needs action (oldest first) with an Action Queue on the dashboard; Leadership land on a read-only Dashboard with an SLA-breach breakdown and cannot submit or change requests

    Live Briefing — Questions & Answers

    #Question AskedOperational Answer
    1Who is allowed to approve or reject requests?Managers only. Staff submit and track; Leadership has read-only dashboard access.
    2When is a request considered overdue?When it is still open (Submitted, Under Review or Approved) more than 7 calendar days after createdAt.
    3Can a rejected or completed request be reopened?No. Rejected and Completed are terminal; the requester raises a new request with updated justification.
    4What employee data may the prototype store?No real personal data. Use anonymized EMP-xxx identifiers and synthetic request content only.
    5How should "time to approval" be measured?Calendar days from createdAt to approvedAt, averaged across Approved and Completed requests.

    Recorded Assumptions

    • Static browser storage: the prototype is a static GitHub Pages site; data persists per browser in localStorage with no backend. A production build would move to the relational schema below.
    • Synthetic identities: all requesters use anonymized EMP-xxx IDs; no names, emails or real employee data are stored.
    • 7-day overdue SLA: a single global threshold (PORTAL_CONFIG.slaThresholdDays) applies to all priorities.
    • Strict state machine: statuses change only through VALID_TRANSITIONS; there is no admin override.
    • Fail-closed CI/CD: if secret scanning, linting or the dependency audit fails, the deploy job does not run.
    • Role switching is a demo convenience, not authentication; production would map roles from SSO.
    • Staff View represents one signed-in employee (EMP-130); only Managers may log requests on behalf of other anonymized EMP-xxx IDs. All role checks run in the browser as defence in depth — production would enforce them server-side.

    Security

    Issue 1 — Staff could impersonate any employee & RBAC relied on hidden buttons

    The generated Staff View included an "Acting as" dropdown listing every EMP-xxx ID, and the submit handler trusted whatever Employee ID was in the input — so a staff user could raise requests as someone else. Status changes were blocked only by hiding buttons. Fixed by locking Staff to one identity enforced in the handler (not read from the DOM), moving the picker to Manager View, and adding a hard role check at the top of transitionRequest().

    // BEFORE
<select id="staffIdentity">…every EMP ID…</select>
requesterId: read("requesterId"), // trusted from DOM

function transitionRequest(id, toStatus) {
  if (!permissions().canTransition) …
    // AFTER
const STAFF_IDENTITY = "EMP-130"; // locked
requesterId: state.role === "Staff"
  ? STAFF_IDENTITY        // enforced, not read
  : read("requesterId"),

if (state.role !== "Manager") {
  showToast("Access Denied: Only Department Managers " +
    "can transition request statuses", "error");
  return false;
}

    Limitation recorded: this is client-side defence in depth. Real access control needs server-side authentication.

    Quality

    Issue 2 — Invisible BOM character failed the lint gate

    The generated CSV exporter prepended a byte-order mark so Excel opens files as UTF-8, but the escape \uFEFF was written into app.js as the raw, invisible U+FEFF character. ESLint failed Gate 2 with Irregular whitespace not allowed (no-irregular-whitespace). Fixed by using an explicit escape sequence.

    // BEFORE — raw U+FEFF hidden before ${csv}
downloadFile(name, `<U+FEFF>${csv}`, "text/csv");
// eslint: 1373:52 error Irregular whitespace
//         not allowed  no-irregular-whitespace
    // AFTER — explicit, visible escape
downloadFile(name, "\uFEFF" + csv,
  "text/csv;charset=utf-8");
    DevSecOps

    Issue 3 — ESLint v8 circular config error

    eslint-plugin-security v2 exports a flat-config object as recommended. Under ESLint v8's legacy .eslintrc format this crashed the lint gate with TypeError: Converting circular structure to JSON. Switched to the legacy preset.

    // BEFORE — .eslintrc.json
"extends": [
  "eslint:recommended",
  "plugin:security/recommended"
]
    // AFTER — .eslintrc.json
"extends": [
  "eslint:recommended",
  "plugin:security/recommended-legacy"
]
    Quality / Deployment

    Issue 4 — Stale cached app.js made features look broken

    After an update the browser served a cached copy of the old app.js alongside the new index.html, so the theme toggle did nothing. Diagnosed by comparing chart colours in a screenshot with the current code, then confirmed in headless Chromium. GitHub Pages also caches assets for ~10 minutes, so reviewers would hit the same problem. Fixed with versioned script URLs, bumped on every release.

    <!-- BEFORE -->
<script src="theme-init.js"></script>
<script src="app.js" defer></script>
    <!-- AFTER — bump ?v= on every release -->
<script src="theme-init.js?v=8"></script>
<script src="app.js?v=8" defer></script>

    End-User Guide

    Staff — submit a request

    1. Choose Staff View in the Role selector; you are signed in as EMP-130 and the portal opens Workflow showing My requests.
    2. Complete Submit New Request — your Employee ID is filled in and locked, so requests are always raised under your own identity.
    3. Fix any red inline messages and submit; your request appears at the top of the queue as Submitted.
    4. Track progress in My Requests on the Dashboard, or click History for the full audit trail.

    Managers — review and approve

    1. Choose Manager View; the queue switches to Needs action, oldest first, with transition buttons on each row. Use Log request on behalf of in the banner to raise a request for a staff member.
    2. Start with overdue (red-edged) rows and click Move to Review; the Dashboard's Action Queue offers the same buttons.
    3. For a decision, open History, add a manager note, and click Approve or Reject.
    4. Once delivered, click Mark Completed on approved requests.

    Leadership — filter KPIs

    1. Choose Leadership View (read-only); the portal opens the Dashboard.
    2. Filter by department, status, priority or date range; all KPIs, charts and the SLA panel update instantly.
    3. Use SLA Breaches to see which departments are behind and the longest-running requests; Reset Filters returns to the full view.

    Developer Handover Guide

    1. Clone and install

    git clone https://github.com/KVKMadithya/eguardian-service-portal.git
cd eguardian-service-portal
npm install

    2. Run locally

    python3 -m http.server 8080
# open http://localhost:8080

    Serve over HTTP rather than opening the file directly so the CSP 'self' source resolves correctly.

    3. Modify the dataset or KPIs

    • Edit records in INITIAL_REQUESTS in app.js, then click Reset Demo Data (or bump STORAGE_KEY) to reload them.
    • KPI logic lives in computeKPIs(); charts in renderCharts(); the SLA in PORTAL_CONFIG.slaThresholdDays.
    • Lifecycle rules live in VALID_TRANSITIONS; role rights in ROLE_PERMISSIONS; per-role views (home tab, default queue, banner text) in ROLE_PROFILES.
    • After changing app.js or theme-init.js, bump the ?v= number on their <script> tags in index.html so browsers don't serve a cached copy.
    • Light/dark colours are CSS variables (:root and .dark) in the <style> block; theme-init.js applies the saved theme before first paint, and applyChartTheme() re-reads them for Chart.js.

    4. Run the security gates locally

    npm run lint
npm run security:audit

    5. Redeploy

    git add .
git commit -m "Describe your change"
git push origin main

    The push triggers the DevSecOps Pipeline; if all three gates pass, the site redeploys to kvkmadithya.github.io/eguardian-service-portal.
