Production SQL — KPI Queries

PostgreSQL queries against the relational requests table that reproduce each dashboard KPI. The demo pins "today" to 2026-10-30; production uses CURRENT_DATE.

1. Open Requests 
SELECT COUNT(*) AS open_requests
FROM requests
WHERE status IN ('Submitted', 'Under Review', 'Approved');
2. Avg Days to Approval 
SELECT ROUND(
         COALESCE(AVG(approved_at - created_at), 0)::numeric, 1
       ) AS avg_days_to_approval
FROM requests
WHERE status IN ('Approved', 'Completed')
  AND approved_at IS NOT NULL;
3. Approval Rate (%) 
SELECT ROUND(
         COALESCE(
           100.0 * COUNT(*) FILTER (WHERE status IN ('Approved', 'Completed'))
           / NULLIF(COUNT(*) FILTER (WHERE status IN ('Approved', 'Completed', 'Rejected')), 0),
           0
         ), 1
       ) AS approval_rate_pct
FROM requests;
4. Overdue Requests (>7 Days SLA) 
SELECT COUNT(*) AS overdue_requests
FROM requests
WHERE status IN ('Submitted', 'Under Review', 'Approved')
  AND created_at < CURRENT_DATE - INTERVAL '7 days';

Submitted ➔ Under Review ➔ Approved ➔ Completed terminal OR Rejected terminal

Sample Dataset

Synthetic, fully anonymized service requests.

Data Generation Methodology

  • 36 records (REQ-1001–REQ-1036) created between 1 Sep and 28 Oct 2026, roughly 3–4 per week, so the trend chart has a realistic shape.
  • Every department, request type, priority and status is represented, so all filters and chart segments have data.
  • Each statusHistory was generated by walking the same state machine the app enforces: Submitted → Under Review (next day) → Approved/Rejected → Completed (two days after approval).
  • 12 open requests are deliberately older than 7 days so the Overdue KPI is populated.
  • Zero real PII: requesters are sequential placeholders EMP-101–EMP-136; approvers are recorded by role ("Manager"), never by name. Titles and descriptions are generic business scenarios.
  • Data lives in the browser's localStorage (eguardian_requests_v1); Reset Demo Data restores the original 36 records.

Problem Statement

eGuardian's internal service requests — access grants, equipment, maintenance, licenses and cloud resources — are currently raised by email and tracked in departmental spreadsheets. Requests get lost between inboxes, there is no consistent approval path or audit trail, requesters cannot see where their request stands, and leadership has no reliable view of backlog, approval speed or SLA breaches. This portal replaces that fragmented process with one centralized request workflow that enforces a fixed approval lifecycle, records who changed what and when, and feeds an executive dashboard of live KPIs.

Target Users

Staff

Employees in any department who raise requests. They need a quick validated form and visibility of each request's status and history.

Managers

Approvers who triage the queue, review, approve or reject with a note, and confirm completion — within a controlled, auditable lifecycle.

Leadership

Executives who need read-only, filterable KPIs on backlog, approval speed, approval rate and SLA breaches across departments.

Live Briefing — Questions & Answers

2When is a request considered overdue?When it is still open (Submitted, Under Review or Approved) more than 7 calendar days after createdAt.
3Can a rejected or completed request be reopened?No. Rejected and Completed are terminal; the requester raises a new request with updated justification.

Recorded Assumptions

  • Static browser storage: the prototype is a static GitHub Pages site; data persists per browser in localStorage with no backend. A production build would move to the relational schema below.
  • Synthetic identities: all requesters use anonymized EMP-xxx IDs; no names, emails or real employee data are stored.
  • 7-day overdue SLA: a single global threshold (PORTAL_CONFIG.slaThresholdDays) applies to all priorities.
  • Strict state machine: statuses change only through VALID_TRANSITIONS; there is no admin override.
  • Fail-closed CI/CD: if secret scanning, linting or the dependency audit fails, the deploy job does not run.
  • Role switching is a demo convenience, not authentication; production would map roles from SSO.

Security

Issue 1 — DOM XSS via raw innerHTML

Generated table-rendering code interpolated user-supplied titles straight into innerHTML. A title such as <img src=x onerror=alert(1)> would execute in every viewer's browser. Fixed with an escapeHTML() sanitizer on every dynamic value, backed by a CSP header.

// BEFORE
row.innerHTML = `<td>${req.title}</td>
  <td>${req.description}</td>`;
// AFTER
function escapeHTML(str) {
  return String(str).replace(/[&<>"'`]/g,
    (ch) => HTML_ESCAPES[ch]);
}
row.innerHTML = `<td>${escapeHTML(req.title)}</td>
  <td>${escapeHTML(req.description)}</td>`;
// + <meta http-equiv="Content-Security-Policy" ...>
Logic

Issue 2 — Unrestricted status dropdown

The first draft offered a free <select> of all five statuses, so a request could jump from Submitted straight to Completed or be reopened after rejection. Replaced with a deterministic VALID_TRANSITIONS state machine and per-transition buttons.

// BEFORE
statusSelect.addEventListener("change", (e) => {
  request.status = e.target.value; // any → any
  save();
});
// AFTER
const VALID_TRANSITIONS = {
  Submitted: ["Under Review"],
  "Under Review": ["Approved", "Rejected"],
  Approved: ["Completed"],
  Rejected: [], Completed: [],
};
if (!canTransition(request.status, toStatus)) {
  showToast(`Blocked: ${request.status} → ${toStatus}`, "error");
  return false;
}
Quality / DevSecOps

Issue 3 — ESLint v8 circular config error

eslint-plugin-security v2 exports a flat-config object as recommended. Under ESLint v8's legacy .eslintrc format this crashed the lint gate with TypeError: Converting circular structure to JSON. Switched to the legacy preset.

// BEFORE — .eslintrc.json
"extends": [
  "eslint:recommended",
  "plugin:security/recommended"
]
// AFTER — .eslintrc.json
"extends": [
  "eslint:recommended",
  "plugin:security/recommended-legacy"
]
Logic / Quality

Issue 4 — NaN% on empty filters & Chart.js canvas leaks

Filtering to a set with no decided requests divided by zero and rendered NaN%. Each re-render also created a new Chart on the same canvas without destroying the old one, causing flicker, stale tooltips and growing memory use. Added zero-guards and .destroy() before each re-create.

// BEFORE
const rate = (approved / decided * 100).toFixed(1) + "%";
deptChart = new Chart(canvas, config);
// AFTER
const approvalRate = decided > 0
  ? (approvedOrCompleted / decided) * 100 : 0;

function createChart(key, config) {
  destroyChart(key); // existing.destroy()
  state.charts[key] = new Chart(byId(key), config);
}

End-User Guide

Staff — submit a request

  1. Choose Staff View in the Role selector.
  2. Open Workflow and complete Submit New Request, using your EMP-xxx ID.
  3. Fix any red inline messages and submit; your request appears at the top of the queue as Submitted.
  4. Click History at any time to see its progress.

Managers — review and approve

  1. Choose Manager View; transition buttons appear in the queue.
  2. Use the status pills or search to find requests, then click Move to Review.
  3. For a decision, open History, add a manager note, and click Approve or Reject.
  4. Once delivered, click Mark Completed on approved requests.

Leadership — filter KPIs

  1. Choose Leadership View (read-only) and open Dashboard.
  2. Filter by department, status, priority or date range; all KPIs and charts update instantly.
  3. Watch Overdue Requests for SLA breaches; use Reset Filters to return to the full view.

Developer Handover Guide

1. Clone and install

git clone https://github.com/KVKMadithya/eguardian-service-portal.git
cd eguardian-service-portal
npm install

2. Run locally

python3 -m http.server 8080
# open http://localhost:8080

Serve over HTTP rather than opening the file directly so the CSP 'self' source resolves correctly.

3. Modify the dataset or KPIs

  • Edit records in INITIAL_REQUESTS in app.js, then click Reset Demo Data (or bump STORAGE_KEY) to reload them.
  • KPI logic lives in computeKPIs(); charts in renderCharts(); the SLA in PORTAL_CONFIG.slaThresholdDays.
  • Lifecycle rules live in VALID_TRANSITIONS; role rights in ROLE_PERMISSIONS.

4. Run the security gates locally

npm run lint
npm run security:audit

5. Redeploy

git add .
git commit -m "Describe your change"
git push origin main

The push triggers the DevSecOps Pipeline; if all three gates pass, the site redeploys to kvkmadithya.github.io/eguardian-service-portal.
